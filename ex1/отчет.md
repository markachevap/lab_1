# 1 задача: сравнение последовательной и параллельной реализаций множества Мандельброта

## 0. Условия задачи 

Написать параллельную программу для нахождения заданного количества точек множества Мандельброта.

Формат входных данных: Запуск из командной строки
./program nthreads npoints,
где nthreads — количество потоков,
npoints — количество точек.


Формат выходных данных: Файл формата csv с координатами
точек множества Мандельброта.


## 1. Цель эксперимента

Сравнить последовательную и параллельную реализации по корректности результата и времени вычислений. 
Для параллельной версии проверить зависимость времени от числа потоков.

## 2. Окружение эксперимента

Заполнить после выполнения команд:

- Процессор (модель): AMD Ryzen 5 5500U with Radeon Graphics 
- Логические процессоры: 12
- Операционная система: Майкрософт Windows 11 Домашняя для одного языка 10.0.26200 
- Компилятор: Microsoft (R) C/C++ Optimizing Compiler Version 19.51.36260 for x86
- Архитектура сборки: 64-разрядная
- Флаги сборки последовательной версии: `/O2 /EHsc`
- Флаги сборки параллельной версии: `/O2 /EHsc /openmp`
- Размер входа (`npoints`): 1000000
- Число повторных запусков для каждого варианта:10
- Итоговая метрика: медиана времени по 10 запускам


## 3. Алгоритмы

### Последовательная версия

Программа последовательно перебирает точки квадратной сетки комплексной плоскости. 
Программа sequential.exe принимает один аргумент: npoints и последовательно обрабатывает все индексы сетки, 
сохраняет результаты в массив и после вычислений записывает координаты найденных точек в mandelbrot_simple.csv

### Параллельная версия

Вычисление каждой точки независимо от остальных, поэтому цикл по индексам сетки распараллелен с помощью OpenMP `parallel for`. 
Число потоков задаётся аргументом `nthreads`, а `schedule(dynamic)` распределяет итерации динамически между потоками.
Программа parallel.exe принимает два аргумента: nthreads и npoints. 
После завершения параллельных вычислений программа записывает найденные точки в mandelbrot.csv.

### Особенность параметра `npoints`

В данной реализации фактическое число проверяемых точек равно sqrt(npoints)^2. Из кода, 33 строка lab1ex1_OpenMP.cpp:

```c++
int n_side = (int)sqrt((double)npoints);   // целая часть корня
int total  = n_side * n_side;              // реальное число точек
```

Поэтому для тестов имеет смысл брать `npoints`, являющийся полным квадратом, например `1000000` (квадрат 1000 × 1000). 
Так же CSV-файл содержит только точки, признанные принадлежащими множеству, а не все проверенные точки.

## 5. Графики и оценка

В файлах в директории лежит изображение с графиками, построенное в питоне на основе расчетов по данным от многократных вызовов выше.

### График 1. Время от числа потоков
На графике показано время вычислений в зависимости от числа потоков. 
Данные взяты напрямую из замеров: для каждой конфигурации (p = 1, 2, 4, 8) по 10 запускам 
взята медиана времени. 

Горизонтальная линия - это медиана по 10 запускам. 
По графику видно, что время падает с ростом p, не линейно и после перехода от 1 к 2 потокам прирост замедляется. 
Параллельная версия на одном потоке чуть медленнее последовательной, предположение: разница = кикие-то расходы OpenMP.

Как считалось: T(p) для каждой конфигурации — медиана 10 значений; T_seq — медиана 10 значений последовательной версии.

### График 2. Ускорение против идеального
График показывает, во сколько раз быстрее стала программа при p потоках по сравнению с одним потоком. 
Идеальное ускорение, которого хотелось бы достичь - это прямая S(p) = p. Если бы каждый поток работал 100% времени по полной, время падало бы ровно в p раз. 

Реальная линия ниже идеальной, и разрыв растёт с числом потоков, следовательно с увеличением p каждый дополнительный поток приносит всё меньше пользы. 

Как считалось: S(p) = T(1) / T(p), где T(1) и T(p) - медианы 10 запусков, а идеал - S(p) = p.

### График 3. Эффективность параллелизации
График показывает, какая доля от каждого потока реально используется, актуальность такого измерения возникла после предыдущего графика. 
Если E = 1, каждый поток работает на 100% (идеал), если E < 1, то часть времени потоки простаивают. 

По графику видно, что при двух потоках эффективность ещё высокая, при четырёх - заметно падает, а при восьми каждый поток используется чуть больше половины времени. 
То есть чем больше потоков, тем меньше отдача от каждого. Вывод: для данного npoints увеличивать число потоков сверх четырёх невыгодно: прирост времени маленький, а эффективность падает.

Как считалось: E(p) = S(p) / p, где S(p) - ускорение из графика 2, p - число потоков.

### График 4. Разброс времени по 10 запускам
На графике ящиков с усами для каждой конфигурации (seq, p = 1, 2, 4, 8) показан разброс времени по десяти запускам. 

Коробки узкие, значит результаты стабильны, медиана хорошо совпадает со средним. Видны единичные выбросы (например, замедление при одном потоке и ускорение при восьми), 
но их мало, и на общую картину они не влияют.

Как считалось: для каждой конфигурации берутся 10 значений времени; коробка - 25-й и 75-й процентили, линия - медиана, усы - min/max без выбросов, точки - выбросы.

## 7. Результаты

### Корректность

**Результат сравнения CSV:** файлы совпали

**Что это означает:** обе реализации работают одинаково корректно

### Производительность

**Наибольшее измеренное ускорение:** 4,82 при 8 потоках.

**Как меняется время при увеличении числа потоков:** 

при переходе от 1 к 2 потокам время падает почти вдвое: 0,4536 -> 0,2427 с

при переходе от 2 к 4 потокам время падает примерно в 1,74 раза: 0,2427 -> 0,1398 с

при переходе от 4 к 8 потокам время падает в 1,49 раза: 0,1398 -> 0,0941 с

То есть с ростом p абсолютный выигрыш от каждого следующего удвоения потоков уменьшается.

**Интерпретация:**  Время уменьшается с ростом числа потоков, вычисления действительно распределяются между потоками, и до 4 потоков ускорение близко к линейному (эффективность 0,94 и 0,81).

Версия OpenMP с одним потоком медленнее последовательной, что может объясняться накладными расходами OpenMP.
