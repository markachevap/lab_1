## Семинар 1. Основы работы с pthreads

## 1 Pthreads: создание и завершение потоков

Pthreads (POSIX Threads) — стандарт POSIX-реализации потоков. Реализации данного API существуют для большого числа UNIX-подобных ОС (GNU/Linux, Solaris, FreeBSD, OpenBSD, NetBSD, OS X).

Для использования в ОС Windows рекомендуется установить WSL (Windows Subsystem for Linux) — тонкий слой виртуализации, который позво- ляет запускать приложения Linux, не покидая привычного окружения Windows. Для установки WSL нужно выполнить следующую команду в PowerShell (запуск от имени администратора):

```
wsl --install
```

После завершения установки запустите программу Ubuntu — это и есть терминал Linux.

Логика управления потоками в pthreads в целом соответствует тако- вой при работе с библиотекой thread в C++. Отметим, что реализация по- токов в C++ в Unix-системах существенно опирается на вызовы функций из pthreads. Библиотека pthreads предоставляет более низкоуровневый доступ к управлению процессом выполнения потоков, что позволяет до- биться более высокой производительности. Поэтому данная библиотека широко используется для создания систем реального времени, высоко- частотной торговли (HFT) и пр.

Функция pthread_detach, напротив, ничего не будет ждать и воз- вращать из потока. Она просто пометит поток как «отсоединенный» и больше ничего не будет делать. Поэтому вторая программа будет работать при любом количестве потоков. [URL 🔗](#page-0)

);

Асинхронное ис- полнение означает исполнение в любой момент (как правило, немедлен- но). ## 2 False sharing

Рассмотрим систему с общей памятью и двумя процессорами.

Пусть x = 7 — общая переменная для двух процессоров, a — пере- менная процессора 1, b, c — переменные процессора 2.

Чему равно b? Если процессор 2 «не знает» об изменении переменной x, сделанном процессором 1, то значение b будет равно 7, в противном случае 120. Обратите внимание, что, даже если кэш-память процессо- ра 1 реализована по модели сквозной записи, то второй процессор все равно может не знать, что ему нужно обратиться к основной памяти за актуальным значением x.

Ситуация, когда процессор «не знает», была ли изменена кэш-строка, с которой он работал, называется некогирентностью кэшей. Применяют- ся следующие способы обеспечения когерентности кэшей: отслеживание и справочник.

При обеспечении когерентности кэшей может возникнуть false sharing: ситуация, при которой процессор вынужден заново загружать кэш-строку, даже если та ее часть, с которой работает данное ядро, не менялась.


Явление false sharing проиллюстрируем на примере задачи умноже- ния матрицы на вектор с построчным разбиением (см. листинг 4). Обращают на себя внимание следующие два принципиальных момен-

Во-первых, время работы программы на одном потоке отличается в зависимости от входных данных. Различие связано с кэш-промахами чте- ния и записи. Промахи записи возникают в строке 71 при попытке об- нулить элемент вектора. Промахи чтения возникают в строке 73 при доступе к компонентам вектора-столбца, на который умножается матри- ца.

Во-вторых, в то время как квадратная матрица и высоко-худощавая матрица позволяют получить близкое к линейному ускорению програм- мы, то толсто-короткая матрица ведет себя намного хуже. На ряде ар- хитектур может наблюдаться даже замедление программы.

Поясним, почему при умножении матрицы 8 на 8 млн на вектор 8 млн ускорение оказывается существенно меньшим, чем в двух других случаях. Это связано с рассмотренным выше false sharing’ом. Типичный размер кэш-строки составляет 64 байта, т.е. 8 чисел типа double. Резуль- тирующая строка y в рассматриваемом случае состоит из 8 чисел типа double, то есть из одной кэш-строки. В различные элементы этого масси- ва разные процессоры пишут свою результаты вычислений. При этом не возникает состояния гонки, ибо каждый процессор работает со своим на- бором индексов. Наборы индексов разных ядер не пересекаются. Однако, в силу того, что весь массив относится к одной строке кэша, при любом


изменении этого массива, каждый процессор считает, что хранящиеся у него значения y более не актуальны и нужно их обновить, обратившись к оперативной памяти. Из-за этого и возникает задержка, объясняющая снижение эффективности.

Отметим, что на самом деле никакой необходимости обновлять дан- ные у процессора нет, ибо каждый процессор изменяет только свою часть массива, не затрагивая область ответственности другого ядра. Отсюда слово false.

Почему описанная проблема не возникает в двум других случаях входных данных? Потому что массив y больше и не умещается в одну строку кэша. Например, если длина y 8 тысяч элементов, то это тысяча строк кэша. Крайне маловероятно, что второй поток будет обрабатывать начало своей части массива в то время как первый поток дошел уже до конца своей части. Следовательно, явление false sharing, скорее всего, не возникнет.

Как решить эту проблему с рассматриваемом случае? Заполнить мас- сив y «мусором» так, чтобы он более не умещался в одну строку.
